# Operational Security Controls & Boundaries

Munin is designed for authorized assessment, threat intelligence, and security automation. Because its capabilities include LDAP enumeration, active scanning tools, and dynamic Python tool forging, operators must establish clear scope boundaries, operational security (OPSEC) policies, and access controls before initiating a session.

---

## 🛡️ Implemented Security Controls

| Domain | Control |
| --- | --- |
| **HTTP MCP Transport** | Requires `MUNIN_MCP_AUTH_TOKEN` Bearer authentication. Empty token requests are rejected unless explicitly running with `MUNIN_MCP_ALLOW_ANON=1` (development loopback only). |
| **Web GUI Security** | Uses same-origin proxying. Only the MCP Bearer token is stored in browser `localStorage`. Turso credentials and LLM API keys remain isolated on the backend server. |
| **LDAP Query Injection** | User input parameters pass through `escape_filter_chars` prior to filter template interpolation, neutralizing LDAP Injection risks (CWE-90). |
| **LLM Provider Endpoints** | Strictly mandates HTTPS or loopback addresses, blocking unsafe internal metadata or non-routable IP ranges. |
| **Soul Governance** | Paths are strictly constrained within `soul/` (CWE-22 protection). Edits are proposed for human review via PRs rather than silently applied. |
| **Tool Forging** | Enforces AST inspection, import allowlists, restricted builtins, execution timeouts, and temporary directory sandboxing prior to registering new tools. |
| **Subagent Delegation** | `graph_forge` enforces explicit tool whitelisting; `munin_wake` rejects unregistered or unauthorized subagents. |
| **Redaction Audit** | Audit loggers automatically redact Bearer tokens, API keys, and secret patterns from logs and timelines. |

---

## ⚠️ Security Boundaries & Limitations

### Tool Sandbox Boundaries
Autogenerated Python tools execute in-process following AST and builtin validation. While this mitigates accidental execution risks, AST validation is not a substitute for VM or container-level OS isolation. For untrusted input, execute candidates inside restricted, read-only containers with restricted capabilities and CPU/memory limits.

### Tool Whitelists
Subagents operate strictly within their defined `tool_whitelist`. However, the risk profile of each tool depends on invocation scope and arguments. Always review the purpose and whitelist before waking a subagent, and monitor execution via `subagent_trace`.

### Human-in-the-Loop
Human-in-the-loop governance provides observability, review, and operational intervention. It is not a blocking synchronous confirmation prompt for every individual tool call.

---

## 📋 Security Recommendations

1. **Keep MCP Bound to Loopback**: Run MCP on `127.0.0.1` locally. If exposing via ngrok or live session tunnels, use robust random Bearer tokens and minimal session durations.
2. **Isolate Credentials**: Store LLM API keys, Turso tokens, and MCP secrets in environment variables or GitHub Secrets. Never commit secrets to code repositories or logs.
3. **Preflight Validation**: Run `munin_diagnostics(mode="deep")` before demonstrations or operations to ensure infrastructure health.
4. **Authorized Targets Only**: Use the included OpenLDAP mock (`akatsuki.com`) for testing. Any external assessment requires written authorization and active preflight policies.
