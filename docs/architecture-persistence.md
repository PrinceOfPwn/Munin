# Munin Architecture & Persistence Specification

## System Components

```text
Web GUI / MCP Client
        │ JSON-RPC + Bearer Authentication
        ▼
FastMCP Server (`munin/mcp/main.py`)
        ├── Native Tools: LDAP, Intel, Memory, Multi-Agent Bus, Diagnostics
        ├── MuninAgent: ReAct Loop + LLM Client
        ├── Tool Registry: Dynamic loading of gen__* tools
        └── SharedStateStore
                 │
        ┌────────┴─────────┐
        ▼                  ▼
  Local SQLite          Remote Turso / libSQL
  (Development)         (Production / Online Sessions)
        │
        ▼
  Orchestrator → Subagent Runner → Episodic Events / Messages / Presence
```

`munin/mcp/main.py` registers the MCP surface. The agent and subagents interact with state via `SharedStateStore` and expose events through MCP tools.

## Shared Database Schema

| Table | Purpose |
| --- | --- |
| `semantic` | Key-value persistent semantic facts (`memory_remember` / `memory_recall`). |
| `episodic` | Ordered event timeline of decisions, tool calls, and agent actions. |
| `procedural` | Registry of autogenerated tools, including durable Python source code. |
| `generated_graphs` | Subagent graph specifications (name, purpose, whitelist, system prompt, reset policy). |
| `agent_wake_queue` | Work queue containing pending and claimed tasks for subagent runners. |
| `agent_presence` | Agent status, heartbeat timestamps, and current active tasks. |
| `agent_messages` | Inter-agent messages and result payloads between Munin and subagents. |
| `shared_intel`, `active_tasks` | Shared threat intelligence repository and task coordination bus. |

## Persistence Backends

### Local SQLite Backend
Without `MUNIN_DB_URL`, state is stored locally in `$MUNIN_DATA_PATH/shared_state.sqlite`. Ideal for local development and offline research.

### Remote Turso / libSQL Backend
When `MUNIN_DB_URL=libsql://...` and `MUNIN_DB_AUTH_TOKEN` are provided, `SharedStateStore` connects directly to Turso with autocommit mode. Every state update commits remotely, making memory, messages, forged tools, and subagent graphs immediately durable across multi-runner CI sessions.

## Tool Forging & Rehydration Protocol

```text
Natural Language Spec
  → ToolForgeSubagent
  → Python Candidate
  → AST Inspection & Import Guard + Sandbox Test
  → registry.register
       ├── munin/generated/<slug>.py (Local file)
       └── procedural: Metadata + Source Code (Turso DB)
  → MCP Tool gen__<slug> Exposed

Next Runner Startup
  → procedural_list(include_source=True)
  → If local file missing, atomically restore from database source_code
  → Import & Register gen__<slug>
```

Durable source code persistence ensures that autogenerated tools automatically survive across container, VM, or CI runner restarts.

## Soul & Human-in-the-Loop Governance

Soul identity files (`identity.md`, `principles.md`, `goals.md`, `skills.md`) are maintained as versioned Markdown files in `soul/`. 
Modifications are submitted via `soul_propose_edit`. When `MUNIN_AUTO_PR=1` and GitHub CLI (`gh`) is available, proposals open a Pull Request on the target branch for explicit human review and approval.
